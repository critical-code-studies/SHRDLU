How the files were stored

The machines, the ITS file system, the disks and backup tapes, and the path each surviving copy took to the bench. Compiled for the bench, 30 September 2026.

Numbers in square brackets refer to the sources at the end. Statements marked "probably", "inferred" or "the record does not say" are not documented in any source found; they are reasoning from the files themselves.

Between 1968 and 1977 SHRDLU was a directory of files on the disks of the MIT Artificial Intelligence Laboratory's PDP-10 computers, written and rewritten under the ITS operating system, copied to magnetic tape by the laboratory's backup program, and in part copied again to other machines and other operating systems. The files the bench holds today reached it by two routes: a copy made in 1987 from a directory restored from backup tape, which Terry Winograd later distributed from Stanford, and copies published since 2018 from files recovered from ITS backup tapes (for the 2024 copy the tape is not identified). This page describes the machines, the file system, the storage media and the conversions each copy passed through, and how each stored file relates to the program that the loader assembled.

1. The machines

The AI Laboratory's PDP-6 arrived in 1964, and ITS was running on it as a time-sharing system by July 1967. A PDP-10 with a KA10 processor followed; when ITS spread to other machines it was given the name AI. The Dynamic Modeling group's KA10 (DM) arrived in 1970, the Mathlab KA10 (ML) became operational in 1972, and the Macsyma Consortium's KL10, named MC, arrived in 1975 [2]. The PDP-10/its project's list of machines gives MC's KL10 as serial number 1038, in use at MIT from 1975 to 1988 [1]. In the mid 1980s DEC donated KS10 machines that took over the names; the names MX and MC were swapped, and the KL10 was shipped to Sweden in 1988 [2]. The sources found do not date the swap, so it is probable, not certain, that the name MC still referred to the KL10 in August 1987.

All of these machines used a 36-bit word. A text file on a PDP-10 stores five 7-bit characters in each word, with one bit left over [4]. The CMU manual for SHRDLU states the program's size in these units: "about 100 to 140K 36-bit words of memory on a PDP-10" [B4].

SHRDLU was developed on AI. A note in the directory, probably from 1973 or 1974 (it refers to a version "created on 4-27-73"), says that "on the A.I. machine" a working version was "always availlable as SHRDLU > DSK SHRDLU" [B5]. By 1987 the directory was on MC: Winograd wrote to John Mallery that he "had looked on AI, but not MC", and Mallery replied that the files had been "on backup tape" and that CENT@AI had retrieved them [B1]. When the directory moved from AI to MC is not recorded.

2. The ITS file system

Names, directories and versions

An ITS file is named by four components: a device, a directory and two file names, each of up to six characters drawn from the upper-case ASCII subset. They are usually written device: directory; fn1 fn2 [3]. The disk is the device DSK:. Its Master File Directory lists the user directories, each of which could hold about 200 files; when more room was needed, an "overflow directory" was often created with the suffix 1 [3]. SHRDLU's files lived in the directory SHRDLU;. The loader also reads compiled files from a second directory, SHRDL1; (for example (FASLOAD GRAPHF FASL DSK SHRDL1)) [B6]. SHRDL1 fits the overflow-directory naming pattern; whether it was created for that reason is not recorded. Lars Brinkhoff's list of directories on the tapes that relate to SHRDLU also includes COPY2, GRAMAR, CNVR, PLNR, TW, TWTAPE, ANDEE, JMH and DDM [19].

The second file name was often a version number. Given as >, it means the latest version when reading and a new, higher version when writing; < means the oldest [3]. This is why the files have names such as GRAMAR 28 or PLNR 182, and why the loader asks for each file by its first name only:

(EVAL (LIST 'UREAD *!?KEY '> 'DSK 'SHRDLU))

reads DSK: SHRDLU; key >, the highest-numbered version present [B6]. A file name need not be numeric: DEMO FLICK, MANUAL CMU, HELP DOC, GRAPHF FASL and SHRDLU (INIT) use the second name for a type or purpose. The convention TS name marks an executable program ("TS" for timesharing) [3].

The listing tools sort numeric second names by number, so that 10 follows 9 [8]. When the files are copied to a Unix file system by the modern tools, DIR; FN1 FN2 becomes dir/fn1.fn2 [5]: SHRDLU; PLNR 182 becomes shrdlu/plnr.182, which is the form of the names in the bench's ITS folders.

Words, bytes and blocks

The directory entry for each file records, among other things, the disk pack it is on, its creation date and time, a reference date, the author, a bit recording whether it has been dumped to tape, and its byte size and length [7]. Disk space was allocated in blocks of 1,024 words (the directory keeps the "word count of last block mod 2000", and 2000 octal is 1,024) [7]. In the 1987 listing, BLOCKL 4 occupies 2,139 words in 3 blocks, and AR0 JAN71 occupies 47,104 words, exactly 46 blocks [B1].

A number such as 2139(36) in the listing is a length followed by a byte size in bits. The ITS directory format provides for byte sizes from 1 to 36 bits, and "old files have UNBYTE=0 => S=36", that is, files written before byte sizes were recorded count as 36-bit files whose length is a number of words [7]. Every file in the 1987 listing has byte size 36 except PLNR 182, shown as 76934(7): 76,934 seven-bit characters, written on 18 August 1987 by a user named AI0 [B1].

Text files: packing, padding and page marks

Because a text file of byte size 36 has a length in whole words, its last word has to be filled out when the text does not end on a five-character boundary. The TECO editor's documentation names "the character used to pad the last word of files written by TECO. Normally 3 (for ^C)", and states that on input "trailing ^C's or ^@'s just before eof are considered padding and are flushed" [11]. This is the origin of the Control-C characters (^C, code 3) found at the ends of the SHRDLU files.

The form feed (^L, code 12) divided a file into pages. TECO reads a file one page at a time, up to the next form feed, and its output commands write a form feed after the buffer [11]. The SHRDLU files carry ^L page marks inside the text and at the end, where it is usually followed by ^C padding. Lines ended with carriage return and line feed.

Authors, dates and the dump bit

On machines configured to keep track of file authors (the switch QAUTHP is set for both AI and MC), each directory entry stores the index of the user who wrote the file [7][12]. The creation date is set when a file is written; the reference date is updated when it is read [7][8]. The "dumped" bit records whether a file has been copied to a backup tape; the DUMP program's incremental mode writes only files whose bit is not yet set [6][7].

Archives, indexes and directory notes

ITS supported archive files, single disk files holding many files with a directory of their own on the first page, readable through the ARC device [9]. The DIR device documentation gives the example DIRAR3: for looking into a user's AR3 archive [8]. The 1987 listing of MC: SHRDLU; contains three such files, AR0 JAN71, AR1 1 and AR2 1 [B1]. Their contents are not recorded, and no copy of them has been found.

The directory also carried notes about itself. #FILES is Dave McDonald's description of the directory (the Stanford file files), which describes each group of files, mentions a cross-reference .INDEX > and "the file LISP >" listing every MacLisp function used, and says that "the files whose first names are 'Z' are the origninal files of the system circa January 1971" [B2]. An earlier description, #FILES INFO, is in the PDP-10/its repository [26]. The file !THIS! !DIR! in the 1987 listing has the same date (29 July 1975) and, once converted, the same length (142 words) as the Stanford file blurb, which is McDonald's note beginning "This directory is maintained by Dave McDonald" and signed "7/29/75 -ddm" [B1][B7]; they are probably the same file.

Source, compiled and executable files

Most of the SHRDLU files are MacLisp source, read by the interpreter with UREAD. Compiled MacLisp is stored in FASL files, which are binary: a FASL file begins with two header words in SIXBIT, *FASL+ and a version, followed by blocks each made of a word of nine 4-bit relocation bytes and up to nine data items [10]. FASL files cannot be read as text. The loader draws some of them from other directories (TRACE FASL and GRINDEF FASL from COM;) and the compiled display code GRAPHF FASL from SHRDL1; [B6].

Executables were saved core images. TS TWDEMO is the demonstration program that replays the dialogue scripted in DEMO FLICK [24]. The directory description #FILES INFO lists MOBY DUMP, "an ancient vintage core dump used for occasional demos", and SHRDLU >, a "core image dunp of the most current, best debugged SHRDLU. linked to by sys;ts shrdlu" [26]. Brinkhoff lists further dumps recovered from the tapes, dated from 1971 to 1974, including SHRDLU; MOBY DUMP and ANDEE; TS SHRDLU [19].

3. Disks and tapes

Disk packs

Later ITS configuration files record the disks of each machine. AI had a Systems Concepts DC-10 disk controller with eight units of the IBM 2314 type [12]; gunkies.org identifies them as Calcomp 215 drives [13]. MC had a DEC RH10 controller with RP04 drives, and later Trident T-300 drives connected through a PDP-11: "3 RP04'S AND 3 T-300'S" [12]. The RP04 used a removable pack compatible with the IBM 3336 and held 88 megabytes [14]. The configurations also set a switch for "reserved disk packs" on both machines [12]. The initial 0 on each line of the 1987 listing, and the #0 in its header, probably refer to disk pack 0, since the directory entry records a pack number for each file [7][B1].

DECtape and magnetic tape

The configuration for AI records that it once had four DECtape units ("used to be 4; R.I.P.") and one magnetic tape unit; MC had no DECtape controller and one magnetic tape unit [12]. MC's tape drive is given as a TU41 in one account, and there is disagreement over whether that model was a 7-track or 9-track drive [13]. The CMU manual assumes DECtape for distribution and warns that a saved core image of SHRDLU is "not, therefor, even remotely close to fitting onto a DECTAPE" [B4].

DUMP and the backup tapes

The ITS program DUMP copied files from disk to magnetic tape and loaded them back. A full dump wrote every file; an incremental dump wrote only files not previously dumped. Each tape had a number, and DUMP kept a tape directory on disk in the directories .TAPE0 and .TAPE1; its FIND command reported which tapes held a given file [6]. A file deleted from disk could therefore be restored from tape with DUMP's LOAD command [5][6].

This is what happened to the SHRDLU directory before 1987: Mallery wrote that "it was on backup tape and CENT@AI retrieved it for some reason" [B1]. Every file in the listing except PLNR 182 shows CENT as its author. It is probable, though no source states it, that files loaded from tape took the name of the user who loaded them. Most files in the listing have the reference date 20 March 1986, which may be the date of that retrieval; the record does not say.

Reading the tapes again

MIT's backup tapes survived. The Tapes of Tech Square (ToTS) collection at the MIT Libraries holds "digital copies of the raw data (images) on the backup tapes and extracted directories of the files" of the AI Lab and the Laboratory for Computer Science "from 1973 to the early 1990s" [16]. The tapes, about 12 tons of them, were read at a data recovery facility [17]. Access has been for research; Brinkhoff wrote in 2020 that MIT had given him access "for research only. I'm not allowed to publish files" [18]. Files released from the collection are published with permission, for example the MIT Libraries' own repository of Micro-Planner files, which were extracted from seven ToTS tape images with the program itstar and which acknowledges Eric Swenson's help in identifying them [20].

itstar reads and writes ITS DUMP tape images on Unix [15]. It expects files in the "ITS evacuate" encoding, "which makes text files look like normal Unix LF line ending files" [4]. A text file extracted this way has lost its carriage returns and its 36-bit word structure; the 36-bit length is recoverable only by counting.

Two groups of SHRDLU files have been published from the tapes:

  • ToTS tape 3100015. In February 2018 Brinkhoff added a SHRDLU directory to the PDP-10/its-vault repository with the commit message "SHRDLU from tid3100015" [21]. Another file from the same tape is described as "Tape 1066, TID 3100015, backed up 03/09/73" [22]. The directory contains earlier versions of the program files (for example smspec.88, smspec.89, syscom.107, syscom.108, dictio.70, newans.58), moby.dump, ts.twdemo, demo.flick, and eight files whose names begin z. (z.answer, z.blocks, z.break, z.dictio, z.gramar, z.mover, z.semant, z.syscom) [21]. These are probably the January 1971 "Z" files described in #FILES. The same tape number appears in the MIT Libraries' list of tape images for Micro-Planner, at the path /tots/part7/from-john-card-1/3100015.tap [20].
  • The 2024 import. On 24 July 2024 Eric Swenson committed to the PDP-10/its repository "the original, unedited files written for an old version of Maclisp" [23]. The commit message and pull request do not say which tape the files came from [23][25]. Given Swenson's work with the ToTS files [20], a ToTS tape is the likely source; this is an inference.

4. Reading the 1987 listing

Mallery sent Winograd "a dired of the directory", headed MC: SHRDLU; [B1]. One line reads:

  0   BLOCKL 4         3   2139(36)        11/03/74 13:31:29 (03/20/86)   CENT

In order: the pack number (probably), the two file names, the number of 1,024-word blocks, the length and byte size, the creation date and time, the reference date in parentheses, and the author [7][B1]. The header line 251 blocks in the files listed totals the blocks column. The line for THTRAC 22 gives the creation year as 01, which cannot be correct; a PLNR; THTRAC 22 on ToTS tape 3100015 is dated 30 August 1971 [20], so the listing's 01 is probably a display fault for 71.

The listing names 36 files. Thirty of them have a counterpart among the 33 Stanford files; the six without one are AR0 JAN71, AR1 1, AR2 1, GRAPHF FASL, GRAPHF STUFF and TS TWDEMO. The remaining three Stanford files, README, file-note and fasl, are not in the listing (see sections 5 and 9). The listing has no file named BLOCKS, although the loader reads BLOCKS > [B1][B6].

5. The Stanford copy

From MC to Stanford

In August 1987 Winograd, then at the Center for the Study of Language and Information at Stanford, asked Mallery how to get copies of the files [B1]. How the copies were made is not recorded. Network file transfer from MC to Stanford was possible at the time (the mail header in the Stanford file fasl shows mail passing between SAIL.STANFORD.EDU and MC.LCS.MIT.EDU in December 1986 [B8]), but this does not show that the files travelled that way.

The Stanford files can be matched against the listing by length. When each line feed in a Stanford file is counted as a carriage return and line feed, and the total is divided by five and rounded up, the result equals the word count in the 1987 listing for 26 of the 30 Stanford files that correspond to listing entries (for example blockl, 2,139 words; gramar, 14,570; dictio, 8,643). plnr, counted the same way, comes to exactly 76,934 characters, the length of the 7-bit PLNR 182 written on MC on 18 August 1987, and unlike the other program files it has no ^C padding at the end. The four that differ are manual (3 words short), parser and thtrac (1 short) and smspec (1 long). These counts were made for this page from the bench's files and the listing [B1]; they indicate that the Stanford copy was taken from the MC directory as it stood in 1987, after the PLNR 182 rewrite, and that the conversion replaced carriage-return and line-feed pairs with single line feeds.

The Stanford names are the ITS first names in lower case, with the version numbers dropped. Where the ITS name was not a program name, the Stanford name says what the file is: files is #FILES 6, blurb is probably !THIS! !DIR!, init is SHRDLU (INIT) (491 words in both), macros is .MACR 21 (872 words in both; its header reads ".MACR 21 ... a precompiler for programmer code"), lisp is LISP USAGE, demo is DEMO FLICK, and manual, help and minih are MANUAL CMU, HELP DOC and MINIH DOC [B1][B2]. The file named fasl is not a compiled file: it is a mail message from Michael Greenwald of Symbolics, dated 22 December 1986, on a Common Lisp reader question, as received by MC [B8]. How it came to stand in the place of a FASL file is not known.

The end-of-file characters

Most Stanford program files end with ^L followed by one ^C. blurb ends with four ^C characters, which bring it to exactly 142 words. help, minih and manual end with runs of NUL characters before the final ^L^C. The conversion to Unix text therefore kept some of the ITS padding and dropped the rest; the rule it followed is not known.

The corrupted block in smspec

Lines 712 to 771 of the Stanford smspec differ from the ITS copy smspec.94, which otherwise carries the same text. The damaged lines contain wrong letters (RSSJODE= for RSSNODE=, MAKEAYM for MAKESYM) and control characters (a backspace in P^HEN for THEN, and NUL characters). Counted for this page: of 51 altered characters in lines of unchanged length, 47 differ by bits changed from 1 to 0, and 33 by a single bit. Assuming the ITS layout, with carriage returns restored, all the altered characters fall between words 4,613 and 5,070 of the file, inside its fifth 1,024-word block. The altered bits fall at many different positions in the word.

This pattern is consistent with damage to one block of stored data, on a disk or a tape record, but the record does not say where it happened. There are three candidate points:

  1. On MC before 1987. The listing gives SMSPEC 96, created 31 October 1976, with 6,894 words, the same length as smspec.94. If version 96 was a copy of 94, it could have been damaged when written, on the backup tape from which CENT restored it, or on MC's disks. The bench holds no ITS copy of version 96 to test this.
  2. In the 1987 transfer.
  3. In later storage or conversion at Stanford. The Stanford file comes to 6,895 words, one more than the listing, so the file changed length somewhere after the listing was made.

From Stanford to the bench

The archive code.tar records its files as owned by user winograd, group graphics, with modification dates of 16 September 1997 and a directory date of 13 September 2003 [B9]. The 1997 date is the date the files were written into that Unix directory, not the date of their contents. Winograd's README gives his address as winograd@cs.stanford.edu and describes the files as "a cleaned up version done by Stu Card, Andee Rubin, and Terry Winograd in 1972" [B3]. The earliest capture of the web directory hci.stanford.edu/~winograd/shrdlu/code/ in the Internet Archive is dated 5 May 2001 [27]. The bench's provenance note records that the SHRDLU pages were not carried over when Winograd's homepage moved to Google Sites, and that the bench keeps the 33 files and code.tar unmodified [B10].

6. The ITS copies in the bench

The bench holds two sets from the PDP-10/its repository.

As found. The folder source/its/as-found/ holds the files of commit ace4248f (24 July 2024), Swenson's import of the unedited files, together with demo.flick, which the repository received earlier, on 14 August 2019, with the TS TWDEMO program [23][24]. The bench's demo.flick is byte-for-byte identical to the one in PDP-10/its-vault from ToTS tape 3100015, backed up in March 1973 [21][22]. All the as-found files use Unix line feeds, as itstar produces [4].

The version numbers of the as-found files match those in the 1987 listing, with two exceptions that the listing explains:

  • smspec.94 is two versions older than the listing's SMSPEC 96.
  • plnr.182 has the same name as the listing's PLNR 182, but the listing's file was rewritten on 18 August 1987. The as-found plnr.182 is a different state: it lays out two functions (THREAD and THAMONG) with other indentation and, converted to ITS form, it is 77,027 characters long, against 76,934 for the 1987 file. The repository's timestamp for it is 12 December 1974 [28].

For the other files, the repository's timestamps agree with the creation times in the 1987 listing to the minute and second, but the hours and months are sometimes shifted (for example, blockl.4 is given as 3 December 1974 18:31:29, against 11/03/74 13:31:29 in the listing) [28][B1]. The source of these shifts is not documented. Because the as-found set includes files dated 31 December 1976 (MORPHO 13, SYSCOM 180) and yet has SMSPEC 94 in place of the version 96 created in October 1976, it may not be a single snapshot of MC: SHRDLU;; which tape or tapes it came from is not recorded.

The as-found set includes files the Stanford set lacks: blocks.144 (the file the loader reads as BLOCKS), graphf.3 (the display code, as source), and twutil.14. It lacks cgram, parser, init and macros. The repository keeps the manuals and help files from the same import under doc/shrdlu; the bench's as-found folder does not include them [23].

Restored. The folder source/its/restored/ holds the repository at commit 173f8220 (23 August 2024), after Swenson's changes to make SHRDLU load, compile and run on a later MacLisp [25][30]. In this repository each edit was committed as a new ITS version, so that plnr.185, gramar.30 and smspec.97 are 2024 files whose numbers continue the ITS sequence; they are not files from the MIT disks. _index.4 and graphf.init entered the repository in Swenson's first commit of changes (8794a3e0), not in the import of unedited files, and their source is not stated [29]. _index.4 is a cross-reference of the kind #FILES calls .INDEX; it indexes older versions (SYSCOM 151, SMSPEC 91).

7. The CMU C1 copy

The CMU manual of 14 August 1972 describes a separate copy. SHRDLU was "coaxed away from MIT's Incompatible Time-sharing System (ITS) and converted to run under the DEC TOPS10 (10-50) operating system by converting MacLisp itself", work done by George Robertson; the CMU version, "named the C1 version", was "current with the MIT version to June 1972" [B4]. TOPS-10 names a disk file with up to six characters, a three-character extension and a project-programmer number, written FILENM.EXT[PRJ,PRG] [31]. The manual's build instructions read the files with (uread plnr c1), (uread trace c1), (uread grind c1), (uread shrdl1 c1) and (uread shrdl2 c1), so the version name took the place of the ITS version number as the second name [B4].

The C1 distribution was a "SHRDLU Kit" of a saved MacLisp, an interpreted Micro-Planner, and SHRDLU "distributed as 2 large files to prevent parts from falling off and for ease in loading", with the boundaries of "the traditional SHRDLU files used for editing" marked by comments such as ;;;[S->GLOBAL] [B4]. Users were told to copy the files to disk with PIP and to use the /B (binary) switch for MacLisp [B4]. No copy of the C1 files has been found; the manual survives as MANUAL CMU on MC and as manual in the Stanford set.
